**مخزن:** `rrasi90/POL-2.3`  
**شاخهٔ ممیزی‌شده:** `ui/visual-qa-screen-completion-20261025`

**دامنه:** Web، Mobile، مسیرها، حالت‌های UI، تطبیق قرارداد API، شواهد طراحی و آزمون

## حکم اجرایی

**فرانت‌اند پل از نظر تعداد صفحات و اجزای پایه تا حد زیادی پیاده‌سازی شده، اما کامل بودن طراحی و رفتار همهٔ جریان‌ها هنوز تأیید نشده است.** در این ممیزی، چند شکاف واقعی عملکردی و چند شکاف مهم پوشش طراحی/QA پیدا شد. این سند ادعای اجرای تست جدید نمی‌کند؛ سورس، مستندات، مسیرهای صفحه و پیکربندی آزمون بررسی شده‌اند.

## یافته‌های عملکردی و طراحی با اولویت بالا

### P1 — فرم تماس عمومی موفقیت کاذب نشان می‌دهد

در `mvp/apps/web/src/app/contact/page.tsx`، تابع `handleSubmit` صرفاً `setSubmitted(true)` را اجرا می‌کند. هیچ درخواست API یا ذخیرهٔ سروری در این تابع وجود ندارد، اما صفحه پیام «پیام شما با موفقیت ثبت شد» نمایش می‌دهد. در نتیجه فرم از نظر ظاهری کامل به نظر می‌رسد ولی ثبت درخواست اثبات نشده است.

**اقدام لازم:** یا endpoint واقعی ثبت درخواست ساخته و به فرم وصل شود و موفقیت فقط پس از پاسخ سرور نمایش داده شود، یا فرم موقتاً به تماس/راه ارتباطی واقعی هدایت شود. آزمون باید ارسال، خطای سرور و موفقیت واقعی را پوشش دهد.

شواهد: [کد فرم تماس، مدیریت submit](https://github.com/rrasi90/POL-2.3/blob/ui/visual-qa-screen-completion-20261025/mvp/apps/web/src/app/contact/page.tsx#L7-L16) و [متن موفقیت](https://github.com/rrasi90/POL-2.3/blob/ui/visual-qa-screen-completion-20261025/mvp/apps/web/src/app/contact/page.tsx#L63-L76).

### P1 — تنظیمات اعلان Native با قرارداد API ناسازگار است

`mvp/apps/mobile/src/screens/AccountMobileScreen.tsx` ترجیحات را به شکل یک شیء `Preferences` شامل `push_enabled`، `sms_enabled` و `email_enabled` می‌خواند و همان شیء را با PUT ارسال می‌کند. اما قرارداد سرور متفاوت است:

- GET از `notification_preferences_get` یک **فهرست** ردیف‌های دسته‌بندی‌شده برمی‌گرداند؛ فیلدهای پایدار آن `user_id`، `category`، `push_enabled` و `sms_enabled` هستند.
- PUT به‌جای کل شیء ترجیحات، `event_name`، `channel` و `is_enabled` می‌خواهد.
- سرویس فقط کانال‌های `PUSH` و `SMS` را می‌پذیرد؛ `EMAIL` در این قرارداد وجود ندارد.

بنابراین مدل داده، نمایش toggleها و درخواست ذخیرهٔ موبایل با API هم‌راستا نیستند؛ کنترل ایمیل نیز فعلاً کانال پشتیبانی‌شده‌ای در backend ندارد.

**اقدام لازم:** الگوی Web که هر ترجیح را برای یک دسته/کانال ذخیره می‌کند با Native یکسان شود؛ یا اگر ایمیل باید پشتیبانی شود، ابتدا قرارداد API و storage توسعه یابد و سپس UI به آن متصل شود. آزمون باید payload واقعی GET/PUT را بررسی کند، نه فقط وجود رشته‌ها در سورس.

شواهد: [مدل و ذخیرهٔ ترجیحات در Native](https://github.com/rrasi90/POL-2.3/blob/ui/visual-qa-screen-completion-20261025/mvp/apps/mobile/src/screens/AccountMobileScreen.tsx#L14-L75)، [قرارداد درخواست](https://github.com/rrasi90/POL-2.3/blob/ui/visual-qa-screen-completion-20261025/scripts/api/schemas.py#L233-L239)، [خواندن و ذخیره در backend](https://github.com/rrasi90/POL-2.3/blob/ui/visual-qa-screen-completion-20261025/scripts/application_boundary.py#L4691-L4717) و [نوع دادهٔ مشترک](https://github.com/rrasi90/POL-2.3/blob/ui/visual-qa-screen-completion-20261025/mvp/packages/types/src/index.ts#L50-L60).

### P1 — تاریخچهٔ پیام‌های پروندهٔ پشتیبانی در Native ناقص است

صفحهٔ `SupportMobileScreen.tsx` پرونده‌ها و جزئیات پرونده را می‌خواند و امکان POST پیام دارد؛ اما endpoint قابل استفاده برای خواندن پیام‌های قبلی در این جریان وجود ندارد. خود UI نیز این محدودیت را اعلام می‌کند. در نتیجه کاربر می‌تواند پیام تازه بفرستد ولی سابقهٔ مکالمه را در این صفحه نمی‌بیند.

**اقدام لازم:** endpoint فهرست پیام‌ها اضافه شود و UI تاریخچه، ترتیب زمانی، وضعیت بارگذاری، خطا، پیام خالی و ارسال موفق را طراحی و آزمایش کند؛ یا قابلیت ارسال پیام تا زمان پشتیبانی کامل تاریخچه محدود/بازطراحی شود.

شاهد: [جریان پشتیبانی Native](https://github.com/rrasi90/POL-2.3/blob/ui/visual-qa-screen-completion-20261025/mvp/apps/mobile/src/screens/SupportMobileScreen.tsx#L48-L118).

### P1/P2 — مدیریت کامل کاربران و سازمان‌ها طراحی و پیاده‌سازی نشده است

صفحهٔ `/admin` صراحتاً `G-007 GAP` و `O-10B` را نشان می‌دهد و توضیح می‌دهد که قرارداد فعلی فقط خواندن اولیه و تغییر وضعیت ادمین را پوشش می‌دهد؛ CRUD کامل وجود ندارد. صفحات کاربران و سازمان‌ها هم فهرست و تغییر وضعیت دارند، نه مجموعهٔ کامل ایجاد/ویرایش/غیرفعال‌سازی و مدیریت چرخهٔ سازمان.

**برداشت:** این مورد یک کمبود واقعی محصول است، اما بخشی از آن وابسته به قرارداد و قابلیت backend است؛ نباید با فرم ظاهری و mutation جعلی پوشانده شود.

**اقدام لازم:** تصمیم محصولی صریح گرفته شود: آیا در MVP مدیریت فقط خواندن/تغییر وضعیت لازم است؟ اگر ایجاد/ویرایش، دعوت، تأیید و KYC لازم است، ابتدا endpoint و سپس فرم‌ها، اعتبارسنجی، تأیید عملیات مخرب و حالت‌های خطا طراحی شوند.

شاهد: [اعلام صریح شکاف G-007 در صفحهٔ مدیریت](https://github.com/rrasi90/POL-2.3/blob/ui/visual-qa-screen-completion-20261025/mvp/apps/web/src/app/(dashboard)/admin/page.tsx#L8-L32).

## پوشش حالت‌ها و شواهد QA کافی نیست

1. **تم شب:** امکان تعویض تم و tokenهای Night در Web وجود دارد، اما در 82 تصویر canonical هیچ تصویر Night/Dark دیده نمی‌شود. در نتیجه داشتن token و toggle، معادل تأیید بصری تم شب روی همهٔ صفحات نیست.
2. **Native Mobile:** تنها 5 تصویر canonical Native در پوشهٔ capture وجود دارد؛ کل 10 ماژول صفحه از نظر Light/Night و حالت‌های مختلف تصویربرداری نشده‌اند. این مجموعه جای تست روی دستگاه/شبیه‌ساز و APK جاری را نمی‌گیرد.
3. **تست بصری:** capture suite چند invariant مفید (مسیر، RTL، زبان، overflow، محتوای خالی نبودن و خطای مرورگر) را بررسی می‌کند؛ اما screenshot baseline comparison یا تشخیص خودکار تفاوت بصری با طرح مرجع ندارد. تصاویر باید در بازبینی جداگانه نیز بررسی شوند.
4. **دسترس‌پذیری:** `a11y.spec.ts` بررسی پایهٔ landmark/heading و نام دکمه‌ها را روی داشبورد خرده‌فروش و بنکدار انجام می‌دهد؛ این معادل ممیزی دسترس‌پذیری تمام مسیرها، کنترل کیبورد، focus، کنتراست و screen reader نیست.
5. **حالت‌های عملیاتی:** تست capture به‌تنهایی حالت‌های loading، error، empty، success، محدودیت مجوز، نبود موجودی، خطای OTP تحویل و رشته‌های طولانی را برای هر مسیر بررسی نمی‌کند.
6. **اعتبار CI:** آخرین اجرای ثبت‌شده، [40188334807](https://github.com/rrasi90/POL-2.3/actions/runs/40188334807)، با failure پایان یافته است؛ هر دو job `steps=null` و بدون log URL گزارش شده‌اند. این مدرکِ شکست assertion تست نیست، اما هیچ اجرای جاری‌ای هم برای تأیید تغییرات فراهم نمی‌کند. تصاویر 82تایی قدیمی‌اند و پس از اصلاحات آخر بازتولید نشده‌اند.

## ناهماهنگی‌های دیداری و متنی باقی‌مانده

- نوار اصلی صفحات احراز هویت‌شده هنوز عبارت انگلیسی `Precision Commerce` را در `app-shell.tsx` نمایش می‌دهد، در حالی که تست واژگان داخلی فقط صفحات عمومی را بررسی می‌کند.
- صفحهٔ تماس هنوز کد داخلی `C-07` را در پیام موفقیت نشان می‌دهد.
- صفحهٔ مدیریت عبارت‌های داخلی `G-007 GAP` و `O-10B` را نمایش می‌دهد.
- در Web، برچسب کانال `PUSH` به «پوش» ترجمه شده؛ «اعلان برنامه» یا «اعلان درون‌برنامه‌ای» طبیعی‌تر و با واژگان Native هماهنگ‌تر است.
- واژه‌گزینی نقش بنکدار/تأمین‌کننده/فروشنده در بخش‌های مختلف یکدست نیست؛ باید یک واژه‌نامهٔ محصولی واحد اعمال شود.
- صفحهٔ عملیات اعلان، لاگ رویدادها را نمایش می‌دهد، اما خودش اعلام می‌کند پیکربندی provider پیامک/اعلان در سرویس پس‌زمینه است. بنابراین تنظیم provider، ارسال broadcast و دیدن وضعیت ارسال از پنل به‌عنوان قابلیت UI کامل نشده‌اند؛ اگر این‌ها نیاز MVP هستند، باید scope و قراردادشان جداگانه تعریف شود.

## مواردی که باید به‌صورت تصمیم دامنه مشخص شوند

- ثبت‌نام خودخدمت و onboarding کامل بنکدار/خرده‌فروش در مسیرهای عمومی دیده نمی‌شود؛ در حال حاضر مسیر عمومی احراز هویت و جریان فعال‌سازی میدانی وجود دارد. اگر فروشنده باید خودش ثبت‌نام و تأیید مدارک را انجام دهد، این یک شکاف طراحی است؛ اگر onboarding در پایلوت فقط توسط کارشناس میدانی انجام می‌شود، باید به‌عنوان تصمیم MVP ثبت شود.
- در مستندات پروژه قید شده است که Driver App جزو دامنهٔ Phase 3 نیست؛ پس نبود آن را کمبود طراحی حساب نکردم.
- بخش‌هایی مثل CRUD کامل مدیریت، تنظیمات provider و تاریخچهٔ پیام پشتیبانی وابسته به API هستند؛ پیش از طراحی mutation باید قرارداد backend تعیین شود.

## ترتیب پیشنهادی رفع کمبودها

1. **ابتدا قراردادها و رفتارهای غلط:** فرم تماس واقعی، تنظیمات اعلان Native و هم‌ترازی کانال‌ها، تصمیم برای تاریخچهٔ پیام پشتیبانی.
2. **سپس شکاف‌های محصولی:** تعیین دامنهٔ G-007 برای کاربران/سازمان‌ها، مشخص کردن نیاز واقعی صفحهٔ مدیریت provider/broadcast و تصمیم onboarding.
3. **سپس تکمیل شواهد صفحه‌ها:** افزودن 14 مسیر محصولی غایب به capture با دادهٔ seeded؛ ثبت دسکتاپ/موبایل‌سایز و Light/Night برای هر سطح لازم.
4. **تست واقعی و بازبینی:** اجرای Web typecheck/lint/build و Playwright، Mobile typecheck/functional/regression/mock QA و Expo build روی SHA جاری؛ سپس بازبینی تصاویر جدید و تست Native روی دستگاه/شبیه‌ساز.
5. **یکپارچه‌سازی UX:** حذف شناسه‌های توسعه از UI، یکنواخت‌سازی واژگان فارسی، افزودن حالت‌های خطا/خالی/موفقیت و گسترش a11y checks.
6. **تطبیق اسناد:** یکی کردن فهرست مسیرهای کد، ماتریس 58سطحی طراحی، ماتریس 68موردی MVP و فهرست capture.

## نتیجه

فرانت‌اند «خالی» یا فاقد طراحی نیست؛ تعداد زیادی صفحه و جریان اصلی وجود دارد. اما در وضعیت فعلی، **نمی‌توان گفت تمام طراحی فرانت‌اند کامل و تأیید شده است**. دو عدم‌تطابق جدی (فرم تماس و تنظیمات اعلان Native)، محدودیت تاریخچهٔ پیام پشتیبانی، شکاف CRUD مدیریت، 14 مسیر محصولی بدون capture و نبود شواهد تازهٔ Night/Native، مانع اعلام تکمیل جامع هستند.

## به‌روزرسانی پس از ممیزی — اصلاحات ثبت‌شده در شاخهٔ کاری

**این بخش وضعیت اصلاحات بعد از ممیزی اولیه را ثبت می‌کند؛ نتیجهٔ آزمون اجرایی نیست.** ممیزی اولیه بر SHA `603e1548998370ad57fc9b3aea1655ae13e9c967` انجام شده بود. پس از آن، تغییرات زیر در همان شاخه ثبت شدند:

1. **تنظیمات اعلان Native:** مدل پاسخ GET با فهرست ترجیحات به‌ازای دسته هماهنگ شد؛ ذخیره‌سازی از قرارداد `event_name/channel/is_enabled` استفاده می‌کند؛ فقط کانال‌های PUSH و SMS نمایش داده می‌شوند. برای جلوگیری از گزارش موفقیت کاذب، خطای ذخیره به کاربر نشان داده و ترجیحات از سرور دوباره خوانده می‌شوند.
2. **تاریخچهٔ پشتیبانی:** مسیر `GET /api/v1/support/cases/{id}/messages`، متدهای مرزی و سرویس canonical اضافه شدند. خواندن تاریخچه ابتدا مجوز مشاهدهٔ همان پرونده را بررسی و ثبت می‌کند؛ کوئری فقط پیام‌های عمومی با `is_internal = FALSE` را برمی‌گرداند. Native تاریخچه را می‌خواند و نویسنده و زمان را نشان می‌دهد. تست HTTP برای تاریخچه، ترتیب پیام‌ها، مخفی‌ماندن یادداشت داخلی و منع دسترسی مستأجر دیگر اضافه شده است.
3. **فرم تماس:** تا زمانی که endpoint واقعی ارسال عمومی پیدا یا ساخته نشده است، UI دیگر نمی‌گوید پیام ثبت شده یا کارشناس تماس می‌گیرد؛ به‌روشنی اعلام می‌کند فرم آنلاین هنوز فعال نیست و داده ارسال یا ذخیره نمی‌شود. این اصلاح جلوی فریب کاربر را می‌گیرد، اما قابلیت ارسال را کامل نمی‌کند.
4. **متن رابط:** برند انگلیسی در AppShell احراز هویت‌شده به عبارت فارسی تبدیل شد؛ نشانگرهای داخلی `G-007` و `O-10B` از سربرگ مدیریت حذف شدند؛ نام کانال اعلان PUSH و نام دسته‌های شناخته‌شده در صفحهٔ تنظیمات اعلان وب فارسی شدند.
5. **پوشش بصری:** تست capture برای مسیرهای `/profile`، `/notifications`، `/notifications/preferences` و `/ops/notifications` گسترش یافته و assertions برای متن فرم تماس، کدهای داخلی و برچسب «پوش» اضافه شده‌اند. در تست تماس، کلیک روی ارسال نباید پیام موفقیت نمایش دهد.

### مواردی که هنوز باز هستند

- فرم تماس به endpoint ذخیره‌سازی، سامانهٔ سرنخ/CRM یا سرویس ایمیل متصل نیست؛ تصمیم و پیاده‌سازی این اتصال هنوز لازم است.
- CRUD کامل کاربران و سازمان‌ها هنوز با قرارداد فعلی API پیاده نشده و نباید با فرم ظاهری یا mutation جعلی پنهان شود.
- ۱۴ مسیر محصولی دیگر که در ممیزی اولیه فهرست شده‌اند هنوز نیاز به capture با دادهٔ seeded و شناسهٔ واقعی دارند؛ افزودن چهار مسیر جدید، کل فهرست را کامل نمی‌کند.
- ماتریس ۴۱/۵۸/۶۸ باید با مسیرها و captureهای جدید دوباره شمارش و به یک inventory واحد تبدیل شود. عددهای مستندات اولیه، تعداد نهایی پس از این تغییرات نیستند.
- تم شب، تمام حالت‌های loading/empty/error/success/permission-denied و دسترس‌پذیری Native روی دستگاه واقعی/شبیه‌ساز هنوز نیازمند شواهد جداگانه‌اند.
- GitHub Actions همچنان پیش از اجرای مرحله‌ها متوقف شده است: jobها `steps=null` و بدون لاگ قابل‌دریافت گزارش شده‌اند. بنابراین هیچ‌یک از تغییرات فوق فعلاً PASS یا runtime-verified اعلام نمی‌شود و تصاویر پیشین هنوز شواهد نسخهٔ جدید نیستند.

### دروازهٔ پذیرش

تا زمان اجرای موفق API tests، Web typecheck/lint/build/Playwright، Mobile typecheck/functional/regression/mock QA و Expo export روی آخرین SHA، بازبینی تصاویر جدید، و تست Native لازم، PR باید Draft بماند. بررسی API پشتیبانی باید حتماً اثبات کند یادداشت داخلی به مصرف‌کنندهٔ تجاری برنمی‌گردد و کاربر یک سازمان نمی‌تواند تاریخچهٔ پروندهٔ سازمان دیگر را بخواند.

## به‌روزرسانی پوشش مسیرها پس از گسترش تست capture

فایل `mvp/apps/web/tests/visual-capture.spec.ts` اکنون برای ۱۳ مورد از ۱۴ مسیر/قالب محصولی که در ممیزی اولیه فاقد capture صریح بودند، جریان capture مبتنی بر دادهٔ seeded تعریف می‌کند: `/profile`، `/notifications`، `/notifications/preferences`، `/ops/notifications`، مسیر جزئیات عملیات با شناسهٔ واقعی سفارش، جزئیات کاتالوگ خرده‌فروش، بررسی/موفقیت تسویه، جزئیات سفارش خرده‌فروش، جزئیات گروه سفارش، مرجوعی سفارش، ویترین بنکدار، تاریخچهٔ قیمت کالای بنکدار و جزئیات سفارش بنکدار.

**این تغییر، پوشش کد آزمون است و نه مدرک ساخته‌شدن تصویر جدید.** اجرای فعلی GitHub Actions هنوز با دو job دارای `steps=null` پایان می‌یابد و آخرین اجرای مشاهده‌شده متعلق به SHA پیش از HEAD فعلی PR است. بنابراین ۸۲ تصویر قبلی همچنان تاریخی‌اند و نباید نسخهٔ جاری را تأییدشده تلقی کنند.

قالب `/field/tasks/[id]` هنوز به fixture قطعی یک وظیفهٔ میدانی واگذارشده نیاز دارد تا مسیر جزئیات با ID واقعی گرفته شود. علاوه بر آن، تست Dark/Night، حالت‌های تعاملی و خطا، capture موبایل Native روی دستگاه/شبیه‌ساز، بازبینی دیداری تصاویر جدید و یکسان‌سازی ماتریس‌های ۴۱/۵۸/۶۸ همچنان باز هستند.
