# اقتصاد واحد پُل

**مرحلهٔ مدل مالی:** A — فرضیه‌محور. تا زمانی که Concierge یا Pilot دادهٔ واقعی تولید نکرده، این سند Forecast یا ادعای سودآوری نیست.

## ۱. واحد سنجش

واحد اصلی، «سفارش تکمیل‌شده» است؛ نه ثبت‌نام، GMV، دانلود اپ یا سفارش ایجادشده.

```text
Revenue / completed order
- Variable cost / completed order
= Contribution / completed order
```

## ۲. ورودی‌های لازم

| ورودی | چرا لازم است؟ | منبع فعلی | وضعیت |
|---|---|---|---|
| ارزش سفارش | پایهٔ سنجش GMV و ارزش سرویس | Concierge / Pilot | ثبت نشده |
| درآمد یا کارمزد واقعی | سنجش مدل درآمدی | توافق Vendor پس از ایجاد ارزش | فرضیه |
| زمان Field/Operations | سنجش هزینهٔ خدمت | Log Concierge | ثبت نشده |
| هزینه/مسئول تحویل | تشخیص اینکه چه کسی هزینه را تحمل می‌کند | Vendor/3PL + سفارش واقعی | ثبت نشده |
| نرخ لغو و استثنا | هزینهٔ پنهان و کیفیت Workflow | Event log | ثبت نشده |
| نرخ Repeat | پایهٔ LTV و ارزش پایدار | رفتار Retailer | ثبت نشده |
| هزینهٔ جذب | سنجش CAC و نقش Field Force | Log زمان/هزینهٔ جذب | ثبت نشده |
| تأخیر/ریسک تسویه | خطر اقتصادی و عملیاتی | ثبت وضعیت پرداخت | ثبت نشده |

## ۳. قواعد مدل

- هر عدد باید `FIELD`، `BENCHMARK`، `ASSUMPTION` یا `CALCULATED` باشد.
- عددهای موجود در بنچ‌مارک‌های تهران یا سایر کشورها فقط `BENCHMARK` هستند؛ جایگزین دادهٔ کلاستر پُل نمی‌شوند.
- کارمزد ۲٪ تصمیم یا Fact نیست؛ فقط یک فرضیهٔ قابل مذاکره پس از اثبات ارزش است.
- در مسیر Concierge، زمان بنیان‌گذار نیز هزینهٔ واقعی است؛ حذف آن از مدل، Contribution کاذب می‌سازد.
- GMV بدون Contribution، Repeat و کیفیت Fulfillment معیار موفقیت نیست.

## ۴. خروجی لازم برای تصمیم سرمایه

پیش از درخواست سرمایه برای Pilot، باید بتوانیم حداقل این سه جدول را با دادهٔ واقعی یا با برچسب فرضیه ارائه کنیم:

1. Funnel: Retailer واجدشرایط → سفارش اول → تحویل موفق → Repeat.
2. Cost to serve: زمان/هزینهٔ عملیات، پشتیبانی و استثنا به ازای سفارش.
3. Contribution scenarios: بدبینانه / پایه / خوش‌بینانه، با ورودی‌های آشکار.

## Flags

**Red Flags:** هر ادعای Payback، CAC یا سودآوری پیش از ثبت هزینهٔ Concierge/Pilot غیرقابل اعتماد است.

**Yellow Flags:** هزینهٔ تحویل، تسویه و حل اختلاف ممکن است مهم‌تر از هزینهٔ سرور یا پرداخت باشد؛ مدل نباید آن‌ها را صفر فرض کند.
