# حرکت و ریزتعامل

## هدف

حرکت فقط زمانی استفاده شود که به فهم تغییر وضعیت، هدایت توجه یا جلوگیری از خطای کاربر کمک کند. انیمیشن تزئینی که خرید عمده را کند یا مبهم می‌کند در اولویت نیست.

## منبع زمان‌بندی

سیستم بصری Precision Commerce:
- micro: 120–160ms
- standard: 160–240ms
- overlay: 200–280ms
- complex: حداکثر 400ms و فقط با توجیه

توکن و implementation جاری بررسی شود؛ این جدول اجازهٔ hardcode کردن زمان‌های جداگانه در همهٔ صفحه‌ها نیست.

## الگوهای پیشنهادی

| تعامل | بازخورد مناسب | محدودیت |
|---|---|---|
| فشردن دکمه | تغییر واضح pressed/disabled | نباید باعث جابه‌جایی layout شود |
| افزودن کالا به سبد | تغییر مقدار/نشان سبد و feedback کوتاه | عدد واقعی، بدون شمارندهٔ ساختگی |
| تغییر تعداد | بازخورد فوری و وضعیت درخواست مشخص | خطای API مقدار قطعی را وانمود نکند |
| ارسال فرم | loading و جلوگیری از submit تکراری | پس از خطا امکان تلاش دوباره حفظ شود |
| باز شدن modal/drawer | حرکت کوتاه و قابل‌پیش‌بینی | focus/دسترسی صفحه حفظ شود |
| تغییر تب/صفحه | انتقال حداقلی، focus و scroll منطقی | محتوای تازه بی‌دلیل از صفحه نپرد |
| خطا/موفقیت | تغییر وضعیت و متن واضح | تکیه به رنگ یا حرکت تنها ممنوع |
| بارگذاری فهرست | skeleton هم‌اندازهٔ دادهٔ نهایی | پرش چیدمان و skeleton نامنطبق ممنوع |

## الزامات

- reduced-motion دستگاه/سیستم رعایت شود.
- حرکت هرگز تنها راه تشخیص وضعیت نیست.
- حرکت نباید submit، نتیجهٔ API یا عملیات مالی را شبیه‌سازی کند.
- پس از بازگشت از خطا، مقدار/فیلتر کاربر بی‌دلیل پاک نشود.
- موشن روی دستگاه میان‌رده از نظر فریم/تأخیر بررسی شود.
- در حالت loading از spinner یا skeleton متناسب استفاده شود، نه هر دو در هر سطح.
- برای عملیات اصلی، state machine قراردادی مقدم بر timing انیمیشن است.
