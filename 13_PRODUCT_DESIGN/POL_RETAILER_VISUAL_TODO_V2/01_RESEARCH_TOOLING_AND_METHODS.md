# تحقیق ابزارها و روش‌های طراحی با هوش مصنوعی

**هدف:** انتخاب حداقل جریان ابزار/ایجنتی که پوشش، انسجام و قابلیت اثبات کیفیت را برای پروژهٔ فعلی افزایش دهد. تحقیق ابزار جای منبع حقیقت محصول را نمی‌گیرد.

## جمع‌بندی اجرایی

برای POL لازم نیست از صفر یک استک طراحی جدید نصب شود. مخزن از قبل دارای سیستم بصری کانونی، توکن‌ها، مهارت اصلاح بصری، قواعد ایمنی، ماتریس صفحه‌ها و اسناد QA است. بهترین انتخاب، ابتدا تکمیل و اتصال منابع فعلی است؛ ابزار جدید فقط در صورت اثبات شکاف اضافه شود.

## معماری توصیه‌شده

1. **منبع حقیقت:** تصمیمات محصول، Master Tree، قراردادها و سند Precision Commerce.
2. **ساختار طراحی:** JSON و دارایی‌های Doory به‌عنوان خط مبنا/شواهد؛ اپ واقعی React Native/Web به‌عنوان هدف رندر.
3. **قواعد ایجنت:** قواعد ایمنی و مهارت‌های موجود در .agents/ و .pol-design/.
4. **اتصال ابزارها:** MCP فقط وقتی ابزار واقعی و مجوز قابل‌استفاده در محیط ایجنت مشخص شد.
5. **کنترل کیفیت:** lint/ساختار + آزمون رفتاری + اسکرین‌شات واقعی + بازبینی انسانی.
6. **حکمرانی:** Master TODO مکمل است، نه منبع حقیقت موازی؛ همهٔ یافته‌ها به شناسه‌های موجود متصل شوند.

## یافته‌های منابع رسمی

### Figma و MCP

اسناد رسمی Figma MCP می‌گویند MCP زمینهٔ ساختاری فایل (لایه‌ها، کامپوننت‌ها، متغیرها و چیدمان) را به ایجنت می‌دهد؛ ایجنت همچنان کد نهایی را می‌سازد و کیفیت به ساختار فایل، زمینه، قواعد و وضوح دستور وابسته است. توصیه‌های رسمی شامل کامپوننت برای اجزای تکراری، Code Connect در صورت دسترسی، متغیرهای طراحی، نام‌گذاری معنادار لایه‌ها، Auto Layout و توضیح رفتارهایی است که از تصویر مشخص نیست.

نتیجه برای POL: اگر Figma در محیط واقعی قابل استفاده است، از آن برای خواندن یا نوشتن ساختاریافته بهره بگیر؛ اما به‌دلیل وجود Doory و قرارداد tool-agnostic، مهاجرت را خودکار نکن.

- https://developers.figma.com/docs/figma-mcp-server/
- https://developers.figma.com/docs/figma-mcp-server/structure-figma-file/
- https://developers.figma.com/docs/figma-mcp-server/mcp-vs-agent/
- https://help.figma.com/hc/en-us/articles/34855090823063-MCP-server-best-practices

### Codex، مهارت‌ها و دستورهای پروژه

مستندات OpenAI، راهنمای پایدار پروژه، مهارت‌های قابل‌بازیابی، MCP و ایجنت‌های فرعی را لایه‌های مکمل می‌شناسد. راهنمای پایدار باید کوتاه و حاوی قواعد همیشگی باشد؛ دستورهای بسیار طولانی و تکراری زمینه را متورم می‌کنند.

نتیجه برای POL: از قواعد ایمنی و مهارت‌های فعلی استفاده شود. AGENTS.md جدید فقط وقتی ساخته شود که هارنس واقعی آن را لازم داشته باشد و مالکیت/عدم تکرار آن روشن باشد.

- https://learn.chatgpt.com/docs/customization/overview

### OpenCode

OpenCode از SKILL.md، عامل‌های اصلی/فرعی و کنترل دسترسی ابزارها پشتیبانی می‌کند. عامل‌ها می‌توانند برای خواندن، ویرایش، اجرای فرمان، وب و وظایف فرعی مجوزهای متفاوت داشته باشند.

نتیجه برای POL: این معماری در صورت استفاده از OpenCode قابل انطباق است، اما فایل‌های مخصوص OpenCode نباید به‌عنوان استاندارد مشترک همهٔ هارنس‌ها تحمیل شوند.

- https://opencode.ai/docs/skills
- https://opencode.ai/docs/agents

### Design Tokens Community Group

فرمت DTCG 2025.10 یک گزارش نهایی گروه اجتماعی برای تبادل توکن بین ابزارهاست؛ استاندارد رسمی W3C نیست و روی مسیر W3C Standards Track قرار ندارد. این قالب برای interchange مفید است، نه به‌عنوان جایگزین منبع معنایی توکن‌های POL.

نتیجه: اگر واردسازی/خروجی‌گرفتن بین ابزارها نیاز واقعی ایجاد کرد، سازگاری و round-trip توکن‌ها را آزمایش کن؛ در غیر این صورت JSON کانونی فعلی را حفظ کن.

- https://www.designtokens.org/TR/2025.10/format/
- https://www.designtokens.org/faq/

### Playwright و آزمون دسترس‌پذیری

Playwright از مقایسهٔ اسکرین‌شات با baseline پشتیبانی می‌کند. برای مقایسهٔ پایدار باید سیستم‌عامل، فونت، نسخهٔ مرورگر و ابعاد رندر تا حد ممکن یکسان باشند. آزمون خودکار axe برخی مشکلات رایج را پیدا می‌کند، اما مستندات Playwright ترکیب آزمون خودکار، ارزیابی دستی و آزمون مشارکتی را توصیه می‌کند.

نتیجه:
- تصویر مرجع و تصویر جدید از محیط همسان تولید شوند.
- تفاوت تصویر به‌تنهایی اثبات خطا نیست؛ علت اختلاف طبقه‌بندی شود.
- آزمون مرورگر را به آزمون دستگاه واقعی موبایل تعمیم نده.
- اسکرین‌شات طراحی‌شده، اثبات رندر runtime نیست.

- https://playwright.dev/docs/test-snapshots
- https://playwright.dev/docs/accessibility-testing
