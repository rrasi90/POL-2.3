# کنترل کیفیت بصری و رگرسیون

## قواعد شواهد

- screenshot معتبر فقط از نسخهٔ واقعی در runtime همان پلتفرم تولید می‌شود.
- mockup/PNG طراحی‌شده می‌تواند مرجع طراحی باشد، اما شاهد اجرای موبایل یا وب نیست.
- captureهای قدیمی با برچسب HISTORICAL / SUPERSEDED مدرک وضعیت جاری محسوب نمی‌شوند.
- تصویر تنها همراه metadata لازم است: commit، branch، دستگاه/viewport، سیستم‌عامل، تم، مسیر، شناسهٔ canonical، حالت، نسخهٔ ابزار و SHA256.
- baseline و تصویر تازه باید در محیط تقریباً همسان گرفته شوند؛ تفاوت فونت/OS/browser/device باید ثبت شود.
- آزمون تصویری باید با آزمون رفتاری و review انسانی تکمیل شود.

## ابعاد و پوشش

برای وب، از viewportهای تعریف‌شده در پیکربندی Playwright استفاده کن و عرض باریک/مرجع/بزرگ را پوشش بده. برای موبایل، اندازهٔ واقعی دستگاه/شبیه‌ساز و اطلاعات چگالی/رزولوشن ثبت شود؛ 390×844 طراحی Doory، به‌تنهایی معادل مشخصات دستگاه واقعی نیست.

حداقل سطح Retailer:
- Auth و OTP
- خانه/کاتالوگ/دسته‌ها
- جزئیات محصول و پیشنهاد تأمین‌کننده
- سبد خالی و پر، چندتأمین‌کننده‌ای
- allocation و checkout
- تاریخچه و جزئیات سفارش
- تحویل/POD، مرجوعی/اختلاف
- پشتیبانی
- فعالیت مالی/فاکتور
- حساب/اعلان/ترجیحات
- تم Light و Night
- حالات loading/empty/error/success برای قابلیت‌های قابل‌اعمال

## پروتکل خط مبنا و پس از تغییر

1. HEAD و نسخهٔ اپ را تثبیت کن.
2. دادهٔ آزمون deterministic و مجاز آماده کن؛ fixture باید با نقش/مجوز و قرارداد واقعی سازگار باشد.
3. مسیر دستی/خودکار به صفحه و حالت هدف را مستند کن.
4. screenshot خام از runtime واقعی بگیر.
5. وجود فایل، قابلیت خواندن، ابعاد، رنگ، جهت، فونت و هویت حالت را تأیید کن.
6. SHA256 و metadata را ثبت کن.
7. تصویر baseline و after را با ابزار diff مقایسه کن.
8. اختلاف‌ها را به یکی از این گروه‌ها تخصیص بده: مطلوب، regression، noise رندر، تفاوت محیط، یا نیازمند بررسی.
9. آزمون رفتار/قرارداد را جدا از مقایسهٔ تصویر اجرا کن.
10. یافتهٔ باز را در registry نگه دار؛ baseline جدید را برای پنهان کردن regression تأیید نکن.

## گیت‌های اجرایی

### ساختار/متن
- QA checker فارسی اجرا شود.
- نویسه‌های عربی، لاتین ناخواسته، اعداد، نیم‌فاصله، جهت متن ترکیبی و کلید ترجمه بررسی شوند.
- توکن‌های خام، importها، typecheck و build بر اساس اسکریپت واقعی پروژه بررسی شوند.

### رفتار
- ورود و OTP با تست مجاز؛ از دادهٔ واقعی مشتری استفاده نکن.
- افزودن/حذف/تغییر مقدار، خالی‌شدن سبد، تخصیص و checkout بررسی شوند.
- کلیک‌های منتهی به API به قرارداد موجود و خطای مشخص متصل باشند.
- مجوزهای owner/staff در UI و backend جداگانه راستی‌آزمایی شوند.
- سفارش چندتأمین‌کننده‌ای: جمع والد، سفارش‌های فرزند و فاکتورها را بررسی کن.
- هر ادعای «سبک/سریع» باید در ابزار profiling یا اندازه‌گیری قابل‌تکرار پشتیبانی شود.

### بصری/دسترس‌پذیری
- Light/Night، RTL، کنتراست، متن طولانی، لمس و حالات disabled/loading/error.
- در وب، آزمون خودکار accessibility (مثلاً axe با Playwright) در صورت سازگاری اجرا شود؛ نتیجهٔ بدون خطا تمام دسترس‌پذیری را ثابت نمی‌کند.
- order/phone/SKU/price bidi isolation بررسی شود.
- screenshot مقایسه شود و هر اختلاف مهم triage گردد.

## گزارش خطا

برای هر defect:
- ID یکتا
- canonical screen ID / route
- commit و environment
- precondition و steps
- expected vs actual
- screenshot/log/trace، همراه SHA256
- شدت P0–P3
- status و owner
- آزمون regression که بعداً مانع تکرار می‌شود
