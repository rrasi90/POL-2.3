# معیارهای پذیرش و تعریف انجام‌شدن

## معیارهای عمومی

یک آیتم زمانی DONE_WITH_EVIDENCE است که:
1. به منبع/شناسهٔ canonical وصل شده باشد.
2. در محدودهٔ مصوب و بدون تغییر semantics اجرا شده باشد.
3. خروجی واقعی در پلتفرم هدف مشاهده یا آزمون شده باشد.
4. شواهد مستقیم به commit و محیط وصل باشند.
5. آزمون‌های مرتبط پاس شده و اثر رگرسیون به مصرف‌کنندگان مشترک بررسی شده باشد.
6. TODO، یافته و گزارش اجرا هم‌زمان به‌روز شده باشند.

## پذیرش محتوایی و ساختاری

- متن فارسی طبیعی، نویسه‌های فارسی، نیم‌فاصله و ارقام صحیح؛ بدون رشتهٔ فنی ناخواسته.
- عنوان کالا، واحد فروش، MOQ، قیمت عمده/تکی، بنکدار و موجودی از دادهٔ سازگار.
- متادیتای مهم در اندازهٔ قابل خواندن و با hierarchy مشخص.
- هیچ عنصر اساسی به دلیل متن طولانی، اندازهٔ کوچک یا RTL خارج از کادر نباشد.
- خلاصهٔ سبد چندتأمین‌کننده‌ای درست و سبد واحد حفظ شده باشد.

## پذیرش سیستم بصری

- توکن‌ها از مرجع کانونی یا نگاشت ثبت‌شده مصرف شوند.
- Light و Night هر دو با بازبینی واقعی پوشش داده شوند.
- نوع متن/فاصله/شعاع/سطوح و تراکم D1 سازگار باشند.
- کارت‌ها و سطوح nested بدون هدف کاربردی ایجاد نشوند.
- آیکون‌ها، دارایی‌ها و fallbackها منسجم باشند.
- کنتراست/اندازهٔ لمس/نام دسترس‌پذیری و RTL آزموده باشند.
- حرکت از توکن کانونی پیروی کند و reduced-motion رعایت شود.

## پذیرش رفتار

- هیچ endpoint، payload، روش HTTP، مجوز، DB schema یا state transition تغییر نکرده باشد مگر اینکه یک تغییر محصول جداگانه و مجاز تعریف شده باشد.
- ورود/OTP با D-018 سازگار باشد.
- سبد واحد، preview تخصیص، checkout و Idempotency-Key حفظ شده باشند.
- گروه سفارش والد و سفارش‌های فرزند/فاکتورهای بنکدار به روش D-022 قابل فهم باشند.
- اقدام owner-only با UI و backend یکسان بماند.
- تحویل سبک‌وزن D-023 حفظ شود و اپ رانندهٔ کامل اضافه نشود.
- هیچ کیف پول، BNPL یا قابلیت دیگر ممنوع/تأییدنشده فعال نشده باشد.
- خطا/بارگذاری/موفقیت نتیجهٔ واقعی را نمایش دهد؛ mock از دادهٔ واقعی تفکیک شود.

## پذیرش فنی

- دستورات واقعی package manager و scripts از package.json/CI خوانده شوند، نه از حدس.
- typecheck/build و تست‌های مرتبط با تغییر اجرا شوند.
- QA checker فارسی و چک‌های ساختاری متناسب اجرا شوند.
- مسیرهای اصلی و حالت‌های موردتغییر در محیط اجرایی هدف تست شوند.
- screenshot comparison در صورت پشتیبانی اجرا شود و تفاوت‌ها triage شوند.
- اگر runtime یا device موجود نیست، آیتم مربوط BLOCKED می‌ماند و از ادعای visual PASS خودداری می‌شود.
- CI جاری از شواهد تاریخی جدا باشد؛ فقط run مرتبط با commit جاری معتبر است.

## پذیرش تصویر

برای هر تصویر:
- شناسهٔ canonical + route/state
- commit SHA و build identity
- device/browser/OS/viewport، theme و scale
- مسیر ذخیره و زمان capture
- فایل سالم/قابل‌خواندن و ابعاد تأییدشده
- SHA256
- baseline/after و نتیجهٔ diff
- دلیل هر baseline update

## پذیرش تحویل

تحویل نهایی باید شامل این موارد باشد:
- TODO تکمیل‌شده با هر آیتم DONE/OPEN/BLOCKED/NOT_APPLICABLE و دلیل
- گزارش یافته‌های بسته‌شده و باز
- لیست فایل‌های تغییریافته و commits
- خروجی آزمون‌ها، وضعیت CI و شواهد واقعی
- شفاف‌سازی محیط‌هایی که اجرا نشدند
- به‌روزرسانی VISUAL_CHANGE_LOG و VISUAL_QA در محدودهٔ مرتبط
- reviewer مستقل
- PR یا commit قابل‌ردیابی، بدون دست‌کاری main تا زمان پذیرش/ادغام

## معیار کامل‌شدن کل کار

کل پروژه فقط وقتی قابل اعلام «تکمیل» است که همهٔ معیارهای قابل‌اعمال پاس باشند یا استثناها با تصمیم مجاز و شواهد ثبت شده باشند. پیاده‌سازی منبعی، اسکرین‌شات mock، build موفق یا تایپ‌چک سبز به‌تنهایی اثبات تکمیل طراحی نیست.
